⚠️ **Medium** - Module 7 adds multi-tool orchestration on top of the existing hybrid-retrieval chat flow. The main risk is keeping provider compatibility and user trust while adding SQL and web-search fallbacks without rewriting the app around native function calling.

# Module 7 Plan: Additional Tools

## Assumptions

- Build on the current local Module 2-6 style codebase already present in the repo, not the stale `PROGRESS.md`.
- Keep the current stateless chat-completions pattern. Do not require provider-native tool calling because the app targets generic OpenAI-compatible endpoints.
- Preserve the current SSE streaming contract and extend it instead of replacing it.
- Keep text-to-SQL scoped to the current user only and treat safety as a first-class requirement.
- Keep web search configurable via environment variables because the app has no admin UI and some local setups should not make outbound web requests by default.

## Target Outcome

After Module 7, the app should:

- answer document-grounded questions with the existing hybrid retrieval flow
- route structured workspace questions to a text-to-SQL tool
- fall back to web search when the knowledge base is insufficient and web search is enabled
- stream one final assistant answer that can cite document, SQL, and web sources distinctly
- surface enough source attribution in the UI that the user can tell where the answer came from

## Proposed Architecture

### 1. Tool orchestration in the chat service

Add a lightweight orchestration layer before final answer generation:

- run hybrid retrieval first
- decide whether structured analytics are needed
- decide whether web search is needed as a fallback
- gather tool outputs
- build one final prompt containing all available tool evidence
- stream the final answer over the existing SSE channel

Use a small structured-output router prompt when possible, with heuristic fallback if routing fails.

### 2. Safe text-to-SQL via isolated SQLite

Do not execute generated SQL against the live Postgres database.

Instead:

- read the current user's structured workspace data from SQLAlchemy
- project it into an in-memory SQLite database
- expose a compact analytics schema such as:
  - `documents`
  - `document_topics`
  - `document_entities`
  - `conversations`
  - `messages`
- ask the model to generate a SQLite `SELECT` query only
- validate the generated SQL before execution
- execute only against the isolated in-memory database

This gives the user a real text-to-SQL tool without cross-user leakage risk.

### 3. Configurable web search provider

Add a small web-search service with environment-driven behavior:

- `WEB_SEARCH_ENABLED`
- `WEB_SEARCH_PROVIDER`
- `WEB_SEARCH_API_KEY`
- `WEB_SEARCH_MAX_RESULTS`
- `WEB_SEARCH_TIMEOUT_SECONDS`

Support at least one zero-dependency path, such as DuckDuckGo HTML scraping, plus a key-based provider path if easy to add without new dependencies.

### 4. Richer attribution without breaking message storage

Keep using the existing `citations` JSON field on `Message`, but widen the payload shape so it can represent:

- document citations
- SQL result citations
- web result citations

Update frontend types and rendering so citation chips remain backward-compatible with existing document citations.

## Execution Strategy

### 1. Add Module 7 config and tool services

Tasks:

- extend backend settings with SQL-tool and web-search config
- add a `workspace_sql` service that:
  - snapshots current-user structured data
  - builds the SQLite schema
  - generates safe SQL through the model
  - executes and serializes results
- add a `web_search` service that returns title, URL, snippet, and domain
- keep dependencies standard-library where possible

Validation:

- SQL tool runs entirely on in-memory SQLite and rejects non-`SELECT` statements
- web-search service fails gracefully when disabled, misconfigured, or offline

### 2. Refactor chat orchestration around tools

Tasks:

- keep `retrieve_relevant_chunks` as the first tool
- add tool-routing logic that can combine retrieval with SQL or web search
- emit additional SSE events for tool status when helpful
- build a final multi-source prompt with explicit citation labels like `[1]`, `[SQL1]`, and `[WEB1]`
- persist the broader citation payload on assistant messages

Validation:

- retrieval-only questions still stream and save messages correctly
- structured workspace questions can cite SQL results
- out-of-knowledge-base questions can cite web results when enabled

### 3. Update frontend attribution and status handling

Tasks:

- widen citation typings to support source-specific metadata
- parse any new SSE status/tool events without breaking current chat streaming
- update the message bubble to render SQL and web citations clearly
- update top-level status text to reflect routing and fallback behavior

Validation:

- old document citations still render
- SQL and web citations render with readable labels and hover details
- sending a message still works for new and existing conversations

### 4. Update docs and smoke coverage

Tasks:

- document new environment variables in `.env.example` and `README.md`
- extend the manual smoke checklist with:
  - SQL-tool questions
  - no-document fallback behavior
  - web search enabled/disabled behavior
- only update `PROGRESS.md` if end-to-end runtime validation actually passes

Validation:

- configuration instructions are sufficient to enable Module 7 locally
- manual smoke covers both successful and unavailable-fallback scenarios

## Recommended Delivery Order

1. Config and backend tool services
2. Chat orchestration and citation model
3. Frontend status and attribution updates
4. Docs and validation

## Main Risks

- OpenAI-compatible local models may be weak at structured JSON or SQL generation. The implementation should include heuristic and validation fallbacks.
- Web search providers can be unstable or blocked locally. The app should degrade cleanly and say when the fallback was unavailable.
- Answer prompts can become too large if SQL and web payloads are dumped verbatim. Tool outputs should be compact and row-limited.
- The current repo already has uncommitted changes in shared files, so patches must preserve local behavior outside Module 7.

## Definition of Done

- The backend can route a question through retrieval, workspace SQL, and optional web search.
- Assistant answers can cite document, SQL, and web evidence distinctly.
- The frontend shows those attributions without breaking existing chat behavior.
- Configuration and manual smoke docs explain how to run and verify Module 7 locally.
