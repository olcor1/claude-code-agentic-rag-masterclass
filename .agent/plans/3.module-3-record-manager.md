⚠️ **Medium** - Module 3 is narrower than Module 2, but it changes document identity, ingestion behavior, and failure semantics. It is still single-pass executable if you keep scope to the current `.txt` / `.md` pipeline and avoid introducing full document revision history.

# Module 3 Plan: Record Manager

## Assumptions

- Build on the current Module 2-in-progress baseline: `documents` are the visible knowledge-base entries, each document has one required `ingestion_job`, and `document_chunks` are fully replaced on successful reprocessing.
- Keep the lifecycle statuses `queued`, `processing`, `completed`, and `failed`. Represent dedupe/change outcomes in a separate field instead of overloading `status`.
- Keep manual uploads only. Introduce an optional `source_key` contract now, but default it from the filename in the frontend until later modules can provide richer source identities.
- Scope Module 3 to the current `.txt` and `.md` support. Multi-format parsing belongs to Module 5.

## Target Outcome

After Module 3, the app should:

- index a new source normally
- skip chunking and embedding when the same source is uploaded again with unchanged content
- reuse the same logical document entry when the same source is uploaded with modified content
- replace old chunks only after the new content has been processed successfully
- expose whether the last upload was `new`, `updated`, or `unchanged`

## Proposed Architecture

Use the existing `documents` table as the record-manager entity instead of introducing a second top-level record table. Add fields that distinguish active indexed content from a newly uploaded candidate:

- `source_key`
- `content_hash`
- `hash_algorithm`
- `version`
- `last_ingestion_result` with values `new`, `updated`, `unchanged`
- `pending_storage_path`
- `pending_content_hash`
- `last_processed_at`

Add:

- a unique index on `(user_id, source_key)`
- a supporting lookup index on `(user_id, content_hash)`

Rationale:

- it keeps the current frontend and retrieval contracts stable: one visible row per logical source
- it reuses the current `Document -> IngestionJob -> DocumentChunk` relationships
- it allows uploads to be staged and promoted only after successful re-indexing

## Execution Strategy

### 1. Lock the record-manager semantics before editing code

Tasks:

- Define `source_key` as the logical identity of a document for one user.
- Define the four state transitions explicitly:
  - new source + new hash -> create and index
  - existing source + same hash -> skip
  - existing source + different hash -> re-index in place
  - failed re-index -> preserve current active content and surface failure
- Define the hashing input as normalized extracted text, not filename or temp storage path. For the current pipeline that means UTF-8 text with newline normalization.
- Define the response contract additions needed by backend and frontend:
  - `source_key`
  - `content_hash`
  - `version`
  - `last_ingestion_result`

Validation:

- Write one concrete example for each of the four transitions above before implementation begins.
- Confirm `status` still means lifecycle state and `last_ingestion_result` means dedupe/change outcome.

### 2. Add the schema and migration path

Tasks:

- Create a migration that adds the record-manager columns to `documents`.
- Backfill existing rows with safe defaults:
  - `source_key = filename`
  - `hash_algorithm = 'sha256'`
  - `version = 1`
- Resolve existing duplicate logical sources before adding the unique `(user_id, source_key)` constraint. Prefer keeping the most recently updated successful row as canonical and renaming or retiring older duplicates in a deterministic way.
- Add the lookup indexes needed for upload-time matching and duplicate checks.
- Update SQLAlchemy models and Pydantic schemas to match the new columns.

Validation:

- Apply migrations from an empty database.
- Apply migrations against a database that already has Module 2-style documents.
- Verify the unique `(user_id, source_key)` constraint succeeds after backfill.
- Verify ORM serialization returns the new fields without breaking existing document endpoints.

### 3. Refactor upload handling to hash first and upsert the logical document

Tasks:

- Introduce a helper that reads normalized text and computes a SHA-256 hash before background processing is queued.
- Extend the upload contract to accept an optional `source_key`; default it from the filename in the frontend.
- On upload:
  - if no existing record matches `(user_id, source_key)`, create a new `Document` with staged `pending_*` values and a queued ingestion job
  - if an existing record has the same active `content_hash`, delete the newly saved temp file, set `last_ingestion_result = 'unchanged'`, do not queue background processing, and return the existing document
  - if an existing record has a different hash, store the new upload in `pending_*`, reset the job to `queued`, and queue background processing
- Add explicit cleanup for temp files on the unchanged path and on any staging failure.

Validation:

- Uploading the same `.md` twice returns the same document id and does not create a second logical document row.
- Uploading a modified version of the same file reuses the same document id and resets the job to `queued`.
- Uploading two different filenames creates two separate logical document rows.

### 4. Promote pending content only after successful processing

Tasks:

- Update `process_document` to read from `pending_storage_path` when present.
- Keep existing chunk rows untouched until the new chunks and embeddings are ready.
- After embeddings are ready, perform the swap in one transaction:
  - delete old chunks
  - insert new chunks
  - promote `pending_storage_path` to `storage_path`
  - promote `pending_content_hash` to `content_hash`
  - increment `version` for changed content
  - set `last_ingestion_result` to `new` or `updated`
  - clear the pending fields
  - mark the document and ingestion job `completed`
- On failure:
  - preserve the active `storage_path` and `content_hash`
  - clear or quarantine the pending file/path
  - mark the document and ingestion job `failed` with an actionable error
- Add a small file-cleanup helper so stale uploads do not accumulate in `backend/uploads`.

Validation:

- Re-indexing modified content changes the chunk set without increasing the number of document rows.
- A forced embedding failure leaves the last successful chunks and query behavior intact.
- Unchanged uploads never call the embedding provider.

### 5. Surface record-manager outcomes through the API and UI

Tasks:

- Extend `DocumentResponse` and frontend `DocumentRecord` types with the new record-manager fields.
- Update the dashboard upload flow so it can distinguish:
  - `new` -> indexing started
  - `updated` -> re-indexing existing document
  - `unchanged` -> already indexed, skipped processing
- Keep the current polling model for now, but make the status line and document badge show the dedupe outcome clearly.
- Keep chat and retrieval pointed at the active document/chunks only. If document ids stay stable, the chat path should not require structural changes.

Validation:

- The UI shows one row per logical source even after repeated uploads of the same file.
- Re-uploading unchanged content results in a visible skipped/no-op message without a polling loop.
- Re-uploading changed content shows the same row move through `queued -> processing -> completed`.

### 6. Tighten documentation and regression coverage

Tasks:

- Update `tests/manual-smoke-checklist.md` with Module 3 checks:
  - first upload
  - unchanged re-upload
  - changed re-upload
  - failed re-index preserves the previous good state
- Update `README.md` and `PROGRESS.md` only after runtime validation passes.
- Add backend tests for:
  - hash computation on normalized text
  - unchanged short-circuit
  - changed-content re-index
  - failed re-index rollback behavior
- If the repo does not yet have a working automated backend test harness, document these tests as explicit follow-up tasks rather than leaving them implied.

Validation:

- Manual smoke passes end to end with one text file edited between uploads.
- Search results after a changed re-upload reflect the new content and no longer cite removed text.
- There is a documented verification that unchanged uploads do not create extra `document_chunks` rows.

## Delivery Order

1. Migration plus model/schema updates
2. Hashing plus upload upsert path
3. Processing swap and rollback behavior
4. API and frontend outcome wiring
5. Manual validation and docs

## Main Risks

- Using `filename` as the default `source_key` can collide for unrelated files with the same name. Keep the API field optional now so later modules or connectors can pass richer identities.
- Existing data may already contain duplicate filenames per user. The migration must handle those rows deterministically before adding the unique key.
- If pending uploads overwrite the active `storage_path` too early, a failed re-index will leave stale chunks attached to the wrong file. Stage first, then promote on success.

## Definition of Done

- Re-uploading unchanged content does not create a new logical document, a new chunk set, or a new embedding run.
- Re-uploading changed content reuses the same logical document and replaces its chunks after successful processing.
- Failed re-index attempts do not destroy the last good indexed state.
- The dashboard and API make it clear whether the last upload was indexed, updated, or skipped.
