**Complex** - Module 5 changes the ingestion contract from "UTF-8 text files only" to "binary uploads parsed into canonical text" and adds the first real delete path. The key is to preserve Module 3 record-manager behavior while widening format support.

# Module 5 Plan: Multi-Format Support

## Assumptions

- Build on the current repo state, not the stale `PROGRESS.md`: the codebase already contains Module 3-style record-manager fields and Module 4-style metadata extraction.
- Keep manual uploads only. No remote connectors, storage providers, or async job queue changes in this module.
- Support `.pdf`, `.docx`, `.html`, and `.md` through Docling, while keeping `.txt` as the existing fallback so current smoke paths do not regress.
- Preserve the current status model:
  - lifecycle: `queued`, `processing`, `completed`, `failed`
  - ingestion result: `new`, `updated`, `unchanged`
- Preserve Module 3 hash semantics: `content_hash` continues to represent normalized extracted text, not raw file bytes.
- Keep retrieval, chunk storage, and metadata extraction attached to the active logical `Document` row.
- Scope delete behavior to terminal documents (`completed` or `failed`) in the first pass. Reject delete for `queued` or `processing` documents to avoid background-task races.

## Target Outcome

After Module 5, the app should:

- accept `.pdf`, `.docx`, `.html`, `.md`, and `.txt` uploads from the dashboard
- parse supported formats into canonical text through a single backend parser abstraction
- keep dedupe and re-index behavior stable across all supported formats
- continue chunking, embedding, metadata extraction, and retrieval from parsed content
- surface parser failures clearly in the API and UI
- let the user delete a document and remove its chunks, ingestion job, and stored files in one operation

## Proposed Architecture

Keep the current `Document -> IngestionJob -> DocumentChunk` model. Do not introduce a second parsed-content table in this pass.

Add one parser service, for example `app/services/document_parser.py`, with a contract like:

- input: `storage_path`, `filename`
- output:
  - `text_for_hashing`
  - `text_for_chunking`
  - `source_extension`
  - `parser_name`

Parser rules:

- `.txt`: native UTF-8 text reader
- `.pdf`, `.docx`, `.html`, `.md`: Docling-backed parser
- unsupported extensions: HTTP 400 with a single consistent error message

Use parser output in two places:

- upload-time hashing in `prepare_document_upload`
- background processing in `process_document`

Recommendation for this module:

- keep raw uploads on disk in `backend/uploads`
- accept the fact that supported binary files will be parsed once during upload hashing and once during background processing
- avoid parsed-artifact persistence for now so the schema stays stable and the module stays teachable
- rely on the existing relational cascades for `document_chunks` and `ingestion_jobs`; add application-level file cleanup for active and pending upload files

Rationale:

- it preserves the current record-manager model instead of re-architecting storage
- it keeps multi-format support localized to the ingestion layer
- it makes cascade deletes mostly an API/service concern, not a schema redesign

## Execution Strategy

### 1. Lock the supported-format and parser contract

Tasks:

- Define the supported extension matrix explicitly:
  - `.txt`
  - `.md`
  - `.pdf`
  - `.docx`
  - `.html`
- Define the canonical extraction contract:
  - `text_for_hashing` is the normalized extracted text used for `content_hash`
  - `text_for_chunking` is the parsed content handed to `chunk_text`, embeddings, and metadata extraction
- Decide how empty or low-text parses fail. A PDF with no extractable text should behave like the current empty-text failure path.
- Keep one source of truth for allowed formats so backend validation and frontend file input do not drift.

Validation:

- Prepare one known-good sample file for each supported format before implementation.
- Prepare one unsupported sample, such as `.csv` or `.pptx`, and one parse-failure sample, such as a scanned PDF with no readable text.

### 2. Add Docling and a dedicated parser layer

Tasks:

- Add Docling to `backend/requirements.txt` and pin a known-good version during implementation.
- Create a parser module that selects the correct parser by extension and returns the shared parser result object.
- Refactor `save_upload_file` so it only persists the raw upload safely; do not decode file contents there.
- Move extension validation out of `save_upload_file` and into the parser selection layer.
- Keep the current `read_document_text` helper only for `.txt`, or replace it entirely with the new parser service so there is one ingestion path.

Validation:

- Parsing a supported file returns non-empty extracted text.
- Uploading an unsupported file returns a 400 without writing confusing partial state to the database.
- A broken or unreadable file surfaces a parser error that is distinguishable from an embedding failure.

### 3. Refactor record-manager hashing around parsed content

Tasks:

- Update `compute_storage_hash` so it uses the parser abstraction instead of raw UTF-8 file reads.
- Ensure `prepare_document_upload` still computes `pending_content_hash` before deciding whether the upload is `new`, `updated`, or `unchanged`.
- Keep `source_key` behavior unchanged so logical identity still comes from the frontend-provided key or filename.
- Preserve the current unchanged-upload short circuit:
  - same `source_key`
  - same extracted-text hash
  - no new ingestion run
  - no temp file left behind
- Confirm that `.md` files continue to behave the same after moving them under the parser abstraction.

Validation:

- Re-uploading the same PDF or DOCX returns the same document id and `last_ingestion_result = "unchanged"`.
- Re-uploading a modified version of the same source reuses the same document id and resets the ingestion job to `queued`.
- Re-uploading the same `.md` file does not regress existing Module 3 behavior.

### 4. Parse multi-format documents during background ingestion

Tasks:

- Refactor `process_document` to parse `candidate_storage_path` through the new parser service instead of `read_document_text`.
- Keep the current ingestion semantics:
  - chunk parsed content
  - embed chunks
  - extract metadata from parsed content
  - swap chunks only after successful processing
- Ensure metadata extraction receives parsed text, not raw binary or HTML markup noise.
- Preserve the current rollback path for failed re-indexes so the last successful active content stays queryable.
- Make parser errors first-class failures in the ingestion job and document error fields.

Validation:

- A PDF, DOCX, and HTML file can complete the full path: upload -> parse -> chunk -> embed -> metadata -> retrieval.
- A parse failure marks the document or ingestion job `failed` without corrupting the last good chunk set.
- Retrieval and citations continue to work without changes to `chat.py`.

### 5. Add cascade delete semantics end to end

Tasks:

- Add a backend delete route, for example `DELETE /documents/{document_id}`.
- Implement a document deletion service that:
  - verifies ownership
  - rejects deletes while `queued` or `processing`
  - captures `storage_path` and `pending_storage_path`
  - deletes the `Document` row
  - relies on database cascade to remove `DocumentChunk` and `IngestionJob` rows
  - removes any raw files from disk after the database delete succeeds
- Return a small success payload or `204 No Content`; keep the contract simple.
- Add a delete control to the knowledge-base UI with a confirmation step and optimistic list refresh.
- Make sure deleted documents no longer appear in retrieval results or metadata filter options after refresh.

Validation:

- Deleting a completed document removes the document row, chunk rows, ingestion job row, and stored file.
- Deleting a failed document also removes any staged pending file.
- Deleting a queued or processing document returns `409 Conflict` with a clear message.

### 6. Tighten docs and regression coverage

Tasks:

- Update `tests/manual-smoke-checklist.md` with format-specific checks:
  - `.pdf`
  - `.docx`
  - `.html`
  - `.md`
  - delete after successful ingestion
  - delete after failed ingestion
- Update `README.md` with new supported formats and any Docling-specific setup notes.
- Update `PROGRESS.md` only after runtime validation passes.
- If there is still no real backend test harness in the repo, write down the targeted tests that should exist:
  - parser selection by extension
  - unchanged upload short-circuit for parsed formats
  - failed parse rollback
  - delete cleanup of active and pending files

Validation:

- Manual smoke passes for at least one sample file per supported format.
- Deleted documents disappear from the dashboard and stop contributing chunks to retrieval.
- Existing `.txt` and `.md` happy paths still work after the parser refactor.

## Recommended Delivery Order

1. Parser contract plus Docling integration
2. Upload-time hash refactor
3. Background ingestion refactor
4. Delete API and UI
5. Manual smoke and docs

## Main Risks

- Docling may have slower cold starts or platform-specific setup friction on local Windows environments. Pinning and local validation matter.
- Parsing during both upload and ingestion means large files are processed twice. That is acceptable for this module, but it is the first optimization candidate if latency becomes painful.
- Hashes now depend on parser output. A Docling upgrade that changes extraction behavior can change `content_hash` even when the source file is unchanged.
- HTML parsing can include navigation or boilerplate content. If Docling output is noisy, the parser layer may need a small cleanup step before chunking.
- Deleting in-flight documents without a real job queue or cancellation model is race-prone. Keep first-pass deletes limited to terminal states.

## Definition of Done

- The dashboard and API accept `.pdf`, `.docx`, `.html`, `.md`, and `.txt` uploads.
- Supported formats are parsed through one backend abstraction, not scattered file-type checks.
- Record-manager behavior still works for multi-format documents:
  - unchanged re-uploads are skipped
  - changed re-uploads reuse the logical document and replace chunks after success
- Chat retrieval and metadata extraction operate on parsed document content without structural chat changes.
- Deleting a terminal document removes its database records and stored files, and the document no longer appears in the knowledge base or retrieval results.
