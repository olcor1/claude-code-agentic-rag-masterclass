# Module 2 Plan: BYO Retrieval + Memory

## Assumptions

- Use **Option A: Replace** from `PRD.md`: remove OpenAI Responses API patterns and standardize on an OpenAI-compatible **Chat Completions** flow.
- Preserve the **existing Ollama-backed chat setup** for completions instead of introducing a provider swap during Module 2.
- Treat the current repo as a **Module 1 scaffold with partial Module 2 pieces already present**. Start with an audit so we preserve useful groundwork and remove only what conflicts with the Module 2 architecture.
- Keep the stack constraints from `CLAUDE.md` / `Agent.md`: raw SDK calls only, Pydantic schemas, SSE chat streaming, RLS on user-owned data, and manual ingestion only.

## Target Outcome

After Module 2, the app should:

- store uploaded files and process them into chunks plus embeddings
- retrieve relevant chunks from pgvector during chat
- manage conversation history in the database and resend it on each chat request
- stream grounded answers from a generic OpenAI-compatible chat endpoint
- surface ingestion progress in the UI with realtime-compatible status updates

## Execution Strategy

Implement Module 2 in six passes. Each pass should leave the repo in a runnable state.

### 1. Audit and lock the architecture

Tasks:

- Inventory all backend/frontend/database references to managed OpenAI concepts such as `Responses API`, managed threads, built-in file search, or any response/thread identifiers that should not survive Option A.
- Inventory the existing local scaffold for reusable pieces: auth, SSE streaming, conversations/messages tables or schemas, document upload endpoints, embedding service, and vector-search code paths.
- Write down the exact compatibility contract for the new chat layer:
  - request shape from frontend
  - stored conversation/message schema
  - retrieval tool input/output shape
  - streamed event format returned over SSE
- Define one ingestion status model for the entire app: `queued`, `processing`, `completed`, `failed`.

Validation:

- Produce a checklist of files/components to remove, refactor, or keep before touching implementation.
- Verify there is a single agreed architecture document in the plan: no remaining ambiguity about Option A vs dual support.

### 2. Normalize the database model for self-managed memory and retrieval

Tasks:

- Confirm or add first-class tables for:
  - `documents`
  - `document_chunks`
  - `conversations`
  - `messages`
  - `ingestion_jobs` as a **required** status model for every uploaded document
- Ensure each table is user-scoped and covered by RLS.
- Ensure `document_chunks` supports pgvector embeddings plus efficient lookup fields:
  - `document_id`
  - chunk index
  - text content
  - embedding vector
  - timestamps
- Ensure `messages` can represent the Module 2 chat loop:
  - role
  - content
  - citation/tool payload if needed
  - created timestamp
- Add or verify vector index and supporting relational indexes.
- Remove Module 1-only schema fields tied to managed threads/files if they are no longer needed under Option A.

Validation:

- Migration runs clean from an empty database.
- A user can create/read only their own conversations, messages, documents, and chunks.
- Vector similarity query succeeds against `document_chunks`.

### 3. Build the ingestion pipeline behind a stable backend contract

Tasks:

- Define the ingestion API flow:
  - upload file
  - persist metadata
  - queue/start processing
  - extract text
  - chunk text
  - embed chunks
  - persist chunks and embeddings
  - update status
- Keep this pass focused on the baseline supported format already available in the scaffold. Do not expand to full multi-format parsing yet; that belongs to Module 5.
- Make chunking rules explicit and configurable enough to teach the concept:
  - target chunk size
  - overlap
  - empty/short document handling
- Make failure states visible and recoverable. A bad file should fail its own document/job record without corrupting chat state.
- Ensure ingestion does not implement deduplication logic yet beyond basic safety checks; content hashing belongs to Module 3.

Validation:

- Uploading a small text/markdown file creates a `completed` document with persisted chunk rows and embeddings.
- Uploading an invalid/empty file surfaces a `failed` state with an actionable error.
- Re-uploading the same file before Module 3 does not break existing data integrity.

### 4. Replace the managed chat flow with stateless Chat Completions + retrieval

Tasks:

- Introduce or refactor a provider-agnostic chat client that targets an OpenAI-compatible Chat Completions endpoint.
- Move memory ownership into the app:
  - load conversation history from `messages`
  - build the request payload from stored history plus the new user message
  - save assistant output back to `messages`
- Implement retrieval as an explicit app-owned tool/function:
  - embed user query
  - retrieve top-k chunks from pgvector
  - apply a relevance threshold
  - serialize citations/context for the model
- Define the grounded-answer prompt contract:
  - answer from retrieved context when sufficient
  - admit uncertainty when retrieval is weak
  - include citations/source mapping in a UI-friendly shape
- Preserve SSE streaming so the frontend contract remains responsive during long generations.
- Remove any remaining direct dependencies on managed file search or managed thread state.

Validation:

- Starting a new conversation stores a user message and streamed assistant reply in the database.
- Continuing an existing conversation includes prior stored history in the model request.
- A question grounded in uploaded content retrieves relevant chunks and produces cited output.
- A question with weak retrieval falls back to a clear "not enough context" behavior instead of hallucinating.

### 5. Wire ingestion status and retrieval UX into the frontend

Tasks:

- Audit the existing dashboard/auth/chat views and map the minimum Module 2 UI changes:
  - upload area
  - document list with status
  - conversation list
  - chat panel with streamed replies and citations
- Update the frontend API client/types to the new Module 2 contracts for:
  - document upload
  - document listing/status
  - conversation/message retrieval
  - chat streaming
- Add realtime-compatible ingestion status updates. If the current local scaffold cannot use Supabase Realtime immediately, isolate the status subscription behind a client abstraction so the UI contract stays stable.
- Make retrieval grounding visible in the chat UI:
  - source snippets or document references
  - error/empty-state messaging
  - disabled/loading states during ingestion and chat

Validation:

- A user can upload a file and watch it move through status changes to completion.
- The completed document appears in the dashboard without a manual refresh strategy leaking into the UI.
- Chat replies stream into the interface and show source references when retrieval succeeds.

### 6. Clean up, document, and validate the end-to-end Module 2 path

Tasks:

- Remove dead Module 1 code paths, schema fields, and UI branches tied only to the managed Responses API approach.
- Update environment/config docs to describe the required Module 2 provider settings and ingestion/retrieval knobs.
- Update the manual smoke checklist for the new happy paths and failure cases.
- Update `PROGRESS.md` only after runtime validation confirms Module 2 is actually working.

Validation:

- Repo search shows no production code paths still depending on managed Responses API semantics.
- Fresh-start manual smoke test passes:
  - sign in
  - upload document
  - wait for completion
  - ask grounded question
  - continue conversation with memory preserved
- Build/test commands already used by this repo pass after the refactor.

## Recommended Delivery Slices

Use these as execution checkpoints:

1. **Slice A:** architecture audit + schema cleanup
2. **Slice B:** ingestion pipeline to completed chunks
3. **Slice C:** stateless chat completions + retrieval + SSE
4. **Slice D:** frontend status/citation wiring + end-to-end cleanup

## Main Risks

- The repo already appears to contain some ingestion and retrieval scaffolding. Refactoring blindly could re-implement existing work or leave conflicting abstractions behind.
- The PRD expects Supabase Realtime while the local scaffold references local Postgres. Keep the status transport abstract until the runtime path is confirmed.
- SSE streaming plus stored message persistence is easy to get subtly wrong. Save ordering, partial-stream handling, and retry behavior need explicit verification.

## Definition of Done

- Managed Module 1 chat/retrieval patterns are removed or fully replaced under Option A.
- Uploading a document results in stored chunks and embeddings.
- Chat uses stored history plus explicit retrieval on every request.
- The UI shows ingestion progress, streamed responses, and retrieval grounding.
- The repo is documented well enough for the next module to build on top of this foundation without re-architecting memory or retrieval again.
